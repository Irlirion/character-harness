# Общий MCP-шлюз

Дата: 2026-10-03. Направление принято пользователем. Статус: спецификация, код ещё не реализован.

## Назначение

Pi и Codex получают возможности харнеса через общий MCP-интерфейс. Шлюз не содержит собственного LLM tool loop: он публикует инструменты, проверяет вызовы и передаёт разрешённые действия исполнителям.

```text
Pi / Codex -> MCP client -> MCP gateway
                           -> policy + validation + journal
                           -> Minecraft worker / Telegram worker
                           -> memory service / workshop service
```

В первой версии gateway находится в доверенном core-контейнере. Отдельный engine подключается по Streamable HTTP с токеном, привязанным сервером к персонажу и аудитории. Состояние и подключения среды принадлежат core, gateway не создаёт их повторно. В первом кодовом срезе привязка одна и каталог содержит только статус и память.

stdio остаётся возможным локальным транспортом, но не используется между контейнерами. Поддержка версии SDK должна быть проверена после установки зависимостей.

## Каталог первой версии

Названия на wire используют подчёркивания для совместимости клиентов. Пространства minecraft.*, telegram.* в предыдущих документах обозначают логические возможности.

| Семейство | MCP tools |
|---|---|
| Minecraft | minecraft_observe, minecraft_inventory, minecraft_start_skill, minecraft_say |
| Telegram | telegram_read_history, telegram_send_message, telegram_inspect_buttons, telegram_press_button |
| Операции | operations_get, operations_cancel |
| Память | memory_search, memory_propose |
| Навыки | skills_list, skills_describe |
| Мастерская | workshop_propose, workshop_get_candidate, workshop_request_test |

Внешние API, расширенное управление Telegram и остальные навыки добавляются по мере реализации. Несуществующие или недоступные возможности не публикуются. workshop_request_test недоступен без готового runner.

## Контекст и полномочия

character_instance_id, engine_session_id и полномочия устанавливает supervisor. Модель не может переключить их аргументом инструмента. task_id и operation_id проверяются на принадлежность. Доступ к аккаунтам, чатам и игровым подключениям определяется bindings. Каталог фильтруется, но каждый вызов дополнительно проверяется: скрытие tools само по себе не является контролем доступа.

MCP resources могут предоставлять сводку персонажа, текущую задачу и описания навыков без секретов. Базовый путь чтения должен работать через tools: поддержка resources конкретным движком проверяется отдельно. Формат skill registry принадлежит харнесу; MCP не заменяет исполняемые навыки.

## Исполнение

```text
Вызов -> schema validation -> policy -> limits
-> запись намерения -> dispatcher -> worker
-> наблюдаемый результат -> verification -> журнал
```

Короткие чтения возвращают структурированный результат с observed_at и state_version. Длительные навыки возвращают operation_id и status=accepted. accepted не означает выполненную цель. Терминальные статусы: succeeded, failed, cancelled; unknown обозначает неопределённый внешний результат и требует сверки.

Отмена MCP-запроса не предполагает автоматической отмены игрового навыка. Для этого используется operations_cancel с подтверждением фактической остановки. Потеря stdio-соединения также не стирает постоянную операцию.

Для изменяющих вызовов engine bridge по возможности устанавливает invocation_id из стабильного идентификатора tool call. Шлюз сохраняет связь с operation_id. Если клиент не предоставляет стабильный идентификатор, повтор после потери ответа сверяется через операции; совпадение аргументов не считается надёжной дедупликацией.

## События и инициатива

Завершение навыка, опасность и новое Telegram-сообщение поступают в core через журнал событий. Планировщик пробуждает персонажа и передаёт нужные изменения движку. MCP notifications могут дополнять этот путь, но не заменяют долговременную доставку и не гарантируют автоматический запуск turn в клиенте.

Быстрые реакции остаются внутри Minecraft worker. При работающем turn supervisor использует поддерживаемую очередь/steering или прерывание; никогда не запускает второй конфликтующий turn той же сессии.

## Новые возможности

Мастерская создаёт кандидата, тестирует и передаёт на независимый допуск. Только допущенная версия попадает в реестр и MCP-каталог. Обновление tools через notifications используется при поддержке клиента; иначе каталог обновляется на границе turn или через пересоздание подключения. Инструмент не может сам расширить полномочия или опубликовать себя без проверки.

## Проверки перед интеграцией

- Одинаковые схемы и результаты доступны через Pi и Codex.
- Персонаж не читает чужую память и не отменяет чужую операцию.
- Разрыв соединения во время изменяющего вызова не вызывает слепого повтора.
- Длительный навык не блокирует получение независимых событий.
- MCP client reconnect восстанавливает каталог, а core сохраняет операции.
- Недоступный runner и неподдерживаемый тип инструмента возвращают явную ошибку.

Источник: [архитектура MCP](https://modelcontextprotocol.io/docs/learn/architecture). Подробности конкретного SDK и движков проверяются при реализации.

## Постоянные обязанности

По [модели постоянного агента](persistent-agents.md) каталог дополняется tools статуса, предложений обязанностей и запросов пробуждения. Исполнение и валидация wakeups принадлежат scheduler core; MCP не является планировщиком времени.
