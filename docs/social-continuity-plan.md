# План: социальная непрерывность Лады

Дата: 2026-10-10. Статус: первый end-to-end storage/context/staging срез реализован и проверен. Поведение памяти и участия в чате на live inference ещё не проверено; scheduler не реализован.

Ориентир: [agent-workplace](https://github.com/3ndetz/agent-workplace). Заимствуем организацию текущего состояния, памяти о сущностях, постоянных целей и проверку собранного контекста. Детали скриптов исходного проекта не проверены; описанные ниже контракты проектируем для нашего харнеса.

## Результат первого среза

Лада узнаёт ранее встреченного участника в той же аудитории, вспоминает подтверждённое событие и собственное обещание, продолжает разговор после перезапуска core/engine. История больше десяти реплик не стирает обещание. Она не заявляет о выполнении игровых действий, которых текущие инструменты не поддерживают.

Первое демо — разговорное обещание: обсудить выбранное название поселения при следующей встрече. Добыча дерева и другие игровые действия требуют отдельного исполнительного среза. Продолжение по входящему сообщению входит в первую версию; самостоятельное пробуждение — в следующий этап.

Текущий Minecraft intake теперь сохраняет все видимые пользовательские сообщения из CHAT, не только обращения к Ладе. Обычный GAME parser остаётся явно opt-in и принимает pinned `<nickname> text` lines. Модель выбирает typed `reply` или `silent`; молчание завершает событие без reply/speech и остаётся видимым в следующих bounded context windows.

## Исходное состояние

- Core нормализует пакет Лады в `{id, name, persona}`; обе модели получают одну личность.
- PostgreSQL хранит события, ответы и текстовые заметки с изоляцией character/audience.
- Контекст содержит до десяти завершённых пар разговора и до 8 000 сериализованных символов истории.
- MCP содержит `memory_search` и `memory_propose`; заметки считаются непроверенными.
- Есть epoch fencing, leases, дедупликация и запись ответа вместе с speech job.
- Структурированных отношений, обязательств, компактного состояния и scheduler пока нет.

## 1. Контракты памяти и происхождения

Сначала определить схемы Zod в `packages/domain` и зафиксировать решение отдельным ADR перед реализацией.

Объекты:

- Entity: внутренний id, character, audience, channel, внешний идентификатор, provenance, отображаемое имя. Имя не является ключом личности; UUID из контекста и неподтверждённый ник различаются.
- Memory fact: субъект, содержание, источник event/reply, время, уверенность, статус observed/inferred/superseded, видимость.
- Relationship: заметка персонажа об отношении, ссылки на основания, версия. Субъективная оценка не становится фактом о человеке.
- Commitment: что обещано, кому, источник reply, срок при наличии, статус open/fulfilled/cancelled, доказательство перехода. Просроченное обещание остаётся открытым.
- Working state: текущая тема, цель, открытые вопросы, ссылки на обязательства, последний значимый event, версия.

Первый срез ограничить людьми; места и предметы добавить после проверки демо. Приватные данные не попадают в состояние другой аудитории. Межканальные identity bindings откладываются до отдельного подтверждаемого владельцем механизма.

Готовность: примеры схем покрывают знакомство, обещание, неподтверждённый ник, противоречие и запрет переноса приватных сведений.

## 2. Хранилище и завершение turn

Добавить следующую свободную SQL-миграцию, зарегистрировать её в `packages/storage/migrate.ts` и создать storage-функции для новых объектов.

Расширить `/engine/complete` необязательным структурированным `memory_delta`. Это предложение модели; core проверяет scope, источники, epoch, версию состояния и допустимые переходы. Старые движки без delta продолжают работать.

Ответ, speech job, принятый delta и отметку завершения события сохранять одной транзакцией. Повтор завершения не создаёт второе обещание и не повторяет speech job. Невалидный delta отклонять отдельно с диагностикой, сохраняя корректный ответ; для конфликта версии не перезаписывать новое состояние старой сводкой. Не запускать дополнительный LLM-вызов для каждого завершения.

Существующие заметки оставить доступными как legacy unverified. Автоматически превращать их в подтверждённые отношения или факты нельзя. Учесть, что сегодня `memory_propose` пишет отдельно: атомарность нового completion не распространяется на такие прежние записи.

Готовность: PostgreSQL-тесты подтверждают дедупликацию, откат транзакции при сбое, scope, stale epoch, конфликт версии и сохранение открытого обещания после рестарта.

## 3. Единая сборка и просмотр контекста

Расширить `packages/domain/conversation-context.ts` и `/engine/input`: стабильная личность, правила, состояние нужной аудитории, релевантные отношения, открытые обязательства, история и текущее событие. Подключить один контракт в `apps/engine/main.ts` и `apps/codex-engine/main.ts`; формат передачи движку может различаться.

Начальные ограничения: состояние до 2 000 сериализованных символов, общий блок социальной памяти до 6 000, история до прежних 8 000. Это стартовые параметры, а не измеренный токен-бюджет. При переполнении первыми сохранять относящиеся к текущему собеседнику обязательства и ограничения; подробности загружать через memory tools. Сам список открытых обещаний не обрезать с потерей данных: использовать отбор, счётчик остальных записей и доступ к полному списку.

Добавить owner-only `inspect-context`: собранный вход для выбранного события, источники, размеры блоков, причины отбора и исключения. Просмотр не захватывает lease, не вызывает модель и не меняет состояние. Секреты не выводятся; память остаётся недоверенными данными и не может менять инструкции или права.

Готовность: оба движка получают одинаковые сведения; обещание старше окна истории присутствует; переполнение ограничено; просмотр не меняет очередь.

## 4. Правила обновления памяти

Добавить общие правила отдельно от persona Лады: сохранять значимые события и собственные обещания, отличать наблюдение от вывода, сжимать рабочее состояние вместо бесконечного добавления, использовать источники. Ядро личности остаётся управляемым человеком.

Delta формируется в том же turn через проверяемый структурированный механизм. Проверить поддержку у обоих адаптеров; предпочтителен инструмент staging с подтверждением при completion, чтобы формат памяти не попадал в пользовательскую реплику. Незавершённые turns не публикуют staged изменения.

Для исправления или сжатия использовать исходные события и структурированные объекты; не создавать цепочку пересказов прежних сводок. Исправления сохраняют историю происхождения. Не требовать новых воспоминаний от каждой короткой реплики.

Готовность: нейтральный разговор не создаёт ложных обещаний; утверждение пользователя не становится подтверждением выполненного действия; изменение памяти не переписывает persona.

## 5. Сквозное демо и оценка

Подготовить сценарий с фиксированными событиями:

1. Участник знакомится с Ладой и обсуждает название поселения.
2. Лада обещает вернуться к двум вариантам при следующей встрече.
3. Проходят более десяти других обменов, затем перезапускаются core и engine.
4. Участник возвращается: Лада узнаёт его и уместно продолжает тему.
5. Другой участник с похожим именем не получает его историю.
6. В другой аудитории приватная память отсутствует.
7. Повторная доставка event/completion не создаёт дублей.

Хранилище, контекст и права проверять детерминированно; поведение модели — отдельным ограниченным прогоном для Pi и Codex с зафиксированной моделью и бюджетом. Синтетическое демо подтверждает логику, живое Minecraft-демо — интеграцию. Недоступность inference не объявлять успешной проверкой поведения.

Критерии выпуска: восстановлено обещание за пределами истории, источник доступен, нет утечек и дублей, ответ соответствует текущим возможностям. Дополнительно измерить размер контекста и стоимость относительно базовой версии. Миграция аддитивная; выключение нового слоя возвращает прежний формат без удаления накопленной памяти.

## 6. Следующий срез: самостоятельное продолжение

После первого демо реализовать минимальные долговременные wakeups согласно `persistent-agents.md`: время/событие, next_review_at, уведомления, бюджеты, дедупликация, pause и восстановление после рестарта.

Связать wakeup с открытым обязательством. При наступлении срока персонаж либо совершает доступное действие, либо сообщает о препятствии по заданной политике. Не поддерживать ожидание непрерывным LLM polling. Исполнение игровых обещаний подключать после появления соответствующих проверяемых инструментов.

Готовность: разговорное напоминание срабатывает после рестарта ровно один раз; paused не пробуждается; неизменившееся состояние не вызывает повторных сообщений.

Реализованное уточнение: `/engine/complete` принимает необязательный `memory_delta` версии 1. Структура проходит Zod-проверку; PostgreSQL слой дополнительно проверяет character/audience/epoch, scope источников и aggregate `base_state_version`. Версия aggregate увеличивается для каждого принятого delta, включая delta без нового `working_state`. Невалидный delta и конфликт версии возвращаются как `memory.status=rejected`, сохраняя ответ. Для ошибок записи используется savepoint. Повтор того же completion возвращает сохранённый результат; другой payload завершённого события получает `completion_conflict`.

Проверка social-memory среза: Node 24.21.0, `tsc --noEmit`, 64/64 теста успешно, 0 skipped; обе PostgreSQL integration suites запускались на изолированной тестовой БД. Текущий social-response срез: Node 24.21.0 typecheck и полный suite 66/66, 0 skipped, включая silent PostgreSQL regressions. Рабочие контейнеры и credentials не использовались.

В `/engine/input` оба adapters получают общий bounded context, aggregate version, память с provenance и отдельные memory instructions. Proposal из `memory_stage_delta` привязывается core к текущим event/epoch, scope и автору; лишь финальный `/engine/complete` публикует его атомарно с reply и optional speech. Незавершённые turns и отложенные события память не публикуют. `memory_social_list` позволяет читать страницы открытых обязательств, которые не уместились в turn budget; сейчас страница ограничена 25 строками, а максимальный offset — 500. `/owner/inspect-context` только читает pending event и текущую память, не захватывает lease и не вызывает inference. Это реконструкция контекста на момент запроса, не исторический snapshot прежнего turn; persona и секреты в ответ не включаются.

Для выкладки применить миграции 006–007 и перезапустить engine adapters: незавершённые turns до migration 007 не имеют `active_event_id`, поэтому их нужно дать истечь/обработать заново. Межканальное связывание людей и подтверждение identity отсутствуют. Live inference не запускался.

Автоматическую мастерскую, графовую БД, экспорт в Obsidian и общий межканальный профиль в этот срез не включали.
