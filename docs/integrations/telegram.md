# Интеграция Telegram

Пользователь подтвердил режим пользовательских аккаунтов: общение и взаимодействие с другими ботами. Библиотека первой версии — Teleproto, TypeScript-клиент MTProto. GramJS архивирован и в своём README рекомендует этот форк. API и совместимость проверяются на закреплённой версии.

## Подключение и идентичность

Отдельный Telegram worker на аккаунт. Первая авторизация выполняется владельцем через локальный login-flow: api_id/api_hash, код входа и при необходимости 2FA. Авторизованная сессия хранится как секрет; она не передаётся модели и не выводится в логи. При потере авторизации worker переходит в auth_required.

Для различимых персонажей нужны разные пользовательские аккаунты. Один аккаунт можно привязать к одному экземпляру или маршрутизировать по чатам, но внешняя отправляющая идентичность остаётся одной. По умолчанию — один аккаунт на персонажа.

Binding связывает account_id, peer_id и при необходимости topic_id с character_instance_id. Идентификаторы Telegram сериализуются строками, чтобы не терять точность. Связь пользователя Telegram с игроком Minecraft создаётся явно, а не по совпадению имени.

## Входящий поток

```text
MTProto update -> нормализация -> inbox/журнал PostgreSQL
-> binding -> память диалога и состояние задачи
-> сборщик контекста -> Pi session
```

Сообщения, изменения, удаления и разрывы подключения преобразуются в типизированные события. Входящий текст сохраняет источник и уровень доверия. Ответ другого бота не получает права менять цели или полномочия персонажа.

Дедупликация зависит от вида update: для сообщения account_id + peer_id + message_id; для редактирования дополнительно версия/время изменения и контрольная сумма. После reconnect выполняется ограниченная сверка истории разрешённых диалогов. Нельзя предполагать, что внутреннее состояние updates библиотеки транзакционно связано с журналом харнеса. Удаления и недоступные сообщения отражаются как пробелы наблюдения.

Исходящие updates маркируются и не становятся новыми поручениями; это предотвращает циклы самоответов. Обработка одного диалога упорядочена, независимые диалоги могут исполняться параллельно.

## Инструменты персонажа

Проектный контракт, не названия методов Teleproto:

```text
telegram.list_dialogs(scope, cursor)
telegram.read_history(binding_id, limit, before?)
telegram.send_message(binding_id, text, reply_to?)
telegram.edit_message(binding_id, message_id, text)
telegram.inspect_buttons(binding_id, message_id)
telegram.press_button(binding_id, message_id, button_ref)
telegram.send_artifact(binding_id, artifact_id)
```

Доступ определяется разрешёнными bindings. Отправка /start, текстовых команд и ответов, чтение reply markup и вызов callback кнопки позволяют взаимодействовать с ботами. Нажатие текстовой reply-кнопки превращается в отправку сообщения. URL-кнопки возвращают ссылку; Mini Apps и web login требуют отдельного адаптера. Кнопки передачи контакта, платежей или иной чувствительной операции проходят отдельную проверку полномочий.

Перед нажатием проверяется актуальность сообщения и кнопки. После действия задача ждёт ответа бота или изменения сообщения с таймаутом. Корреляция учитывает peer, reply_to, последовательность сообщений и ожидаемое состояние диалога; единого request_id для ответа любого бота нет. Неподдерживаемый тип кнопки возвращает явную ошибку.

## Отправка и восстановление

Исходящие действия сохраняются в outbox. FLOOD_WAIT переводит действие в ожидание до разрешённого времени и не запускает цикл повторных вызовов модели. Ограничения времени и объёма задаются на аккаунт и диалог.

Для MTProto методов с random_id адаптер сохраняет этот идентификатор до отправки и повторно использует его при допустимом повторе; нужно проверить, что библиотека не генерирует новое значение. Сохраняются message_id и исходный результат API. Операции без соответствующего механизма сверяются отдельно; потерянный ответ может означать unknown, а не failure.

## Проверки первой версии

Авторизация и восстановление сессии, получение и отправка сообщений, взаимодействие с тестовым ботом через текст и callback-кнопки, редактирование сообщений, reconnect, дубли событий, FLOOD_WAIT и изоляция аккаунтов. Рабочие аккаунты не используются для автоматических тестов.

Источники: [Teleproto](https://github.com/sanyok12345/teleproto), [документация](https://docs.teleproto.dev/), [статус GramJS](https://github.com/gram-js/gramjs), [Telegram API](https://core.telegram.org/api).

## MCP-интерфейс

Возможности адаптера публикует [общий MCP-шлюз](../mcp-gateway.md). Привязку персонажа и полномочия устанавливает supervisor, а не аргументы модели. События и завершение операций доставляются в core независимо от MCP-соединения.
