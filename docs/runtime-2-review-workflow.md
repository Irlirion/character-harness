# Runtime 2.0: reviewer bridge и разбор блокировок

Четвёртый инфраструктурный срез. Реализованы ограниченный интерфейс отдельного
проверяющего процесса и workflow повторной проверки. Семантическая модель и её
изоляция ещё не аттестованы; production автоматически не включается.

## Подключение

Core читает `RUNTIME_REVIEWER_CONFIG_FILE` только при включённом runtime storage.
Конфигурация — локальный операторский JSON, недоступный для изменения агентом:

- `executable`, `args`, `cwd`: абсолютный путь исполняемого файла и каталога,
  фиксированные аргументы; shell не используется.
- `policy_versions`: точный список версий профиля, для которых проверены правила.
- `rules`: операторский текст правил OpenAI и базового профиля ЕС, 100–30000 символов.
- `rules_hash`: `fingerprint(rules)` из runtime policy; проверяется при запуске.
- `privacy_reviewed: true`, `expires_at`: подтверждение оператором проверки передачи
  данных этому компоненту и срок действия конфигурации. Это декларация оператора,
  а не автоматически выполненная правовая проверка.
- `timeout_ms`: 100–60000; `max_requests_24h`: 1–1000.

Отсутствие файла сохраняет default deny. Некорректный файл прерывает запуск core.
Истёкшая конфигурация, неизвестная версия профиля, занятость или исчерпанный бюджет
возвращают `needs_review`. Профиль исполнения по-прежнему устанавливается отдельно
через внутренний операторский API хранилища. HTTP не позволяет менять правила.

Bridge получает одну JSON-строку через stdin:
`protocol: runtime-review.v1`, `rules`, `rules_hash`, `phase`, `payload`,
`payload_hash`, `policy_version`. В stdout требуется ровно один JSON-объект
`verdict`, `rule_id`, `payload_hash`, `policy_version`; дополнительные поля запрещены.
Hash и версия должны совпадать с запросом. Максимум stdout — 4096 байт.
Ошибки, неверный формат, timeout и отмена не разрешают работу. stderr отбрасывается.
Payload не попадает в командную строку или журналы reviewer bridge.

Один экземпляр bridge обрабатывает один запрос за раз. Каждая попытка до старта
процесса резервируется в PostgreSQL: общий суточный лимит персонажа охватывает все
аудитории и сохраняется после перезапуска. Неудачные попытки не возвращают резерв.
Это лимит запусков reviewer, не токенов, внутренних API-запросов или денег.
Проверки входа и выхода расходуют отдельные попытки.
При первой оценке hash правил фиксируется для версии политики в БД. Изменение
правил при той же версии блокирует reviewer; требуется новая версия профиля.

Процесс получает только `LANG`, без токенов core, DATABASE_URL, API keys и HOME.
Сам исполняемый файл — доверенный операторский компонент: этот интерфейс **не
является sandbox** и не запрещает ему читать доступные ОС файлы или запускать
дочерние процессы. На Unix bridge запускается в отдельной группе процессов; при завершении/отмене
группа уничтожается, включая дочерний App Server. На Windows уничтожается прямой
процесс; управление деревом и изоляцию обеспечивает deployment. Нельзя направлять этот путь на произвольный агентский код.

## Очередь владельца

`GET /owner/runtime-reviews` показывает до 100 актуальных блокировок текущей версии
activity и политики: идентификаторы, hashes, verdict, rule и время, без prompts.
Устаревшие блокировки скрываются. Существующее inspect позволяет владельцу отдельно
посмотреть activity в своей аудитории.

`POST /owner/runtime-reviews/retry` принимает строго:
`request_id` (UUID), `activity_id`, `activity_version`, `policy_version`, `payload_hash`.
Только `needs_review` можно поставить на повторную оценку. `deny` не снимается.
Транзакция проверяет audience, текущие версии и hash; повтор того же request_id
идемпотентен, подмена его параметров отклоняется. На одну версию activity и policy —
не более трёх повторов, интервал минимум минута. История попыток сохраняется.

Повтор снимает hold, но не выдаёт grant, не запускает модель и не возвращает бюджет.
Следующий claim заново собирает содержимое и проходит все gates. Возобновление
отклонённого output означает новый planning turn после штатного recovery; старый
отклонённый checkpoint никогда не сохраняется. Права владельца не заменяют policy.

Оба маршрута требуют owner token, запрещают browser Origin, используют общий
rate limit владельца и `Cache-Control: no-store`. Маршрута `approve` нет.

## Граница с Codex

В этом срезе встроенного семантического Codex reviewer нет. App Server позволяет
управлять потоками и sandbox, но read-only не доказывает отсутствия всех native
инструментов. Прежде чем подключить мост к подписке, нужны проверка фактического
каталога/изоляции, account eligibility, privacy и качества классификатора.
Документация протокола: [OpenAI App Server](https://learn.chatgpt.com/docs/app-server).
Новые платные API, живые вызовы моделей и изменения production не выполнялись.

Миграция `014-runtime-review-workflow` добавляет только счётчик reviewer dispatches
и журнал повторных оценок; старые activity/grants не переписываются. Полный retention,
удаление данных, media/disclosure gates и live pilot остаются отдельной работой.

## Проверки

176 тестов прошли без пропусков; проверка типов пройдена. Покрыты строгий ответ
bridge, неверный hash, timeout, отмена, лимит вывода, отсутствие секретов в окружении,
роли HTTP, scope/stale/replay повторов, запрет снятия deny, cooldown, durable budgets,
привязка правил к версии и полный input/output путь на синтетическом процессе.
Обновление 013 → 014 и повторный запуск всех 15 миграций проверены в отдельной
временной схеме; существующие данные сохранены.
