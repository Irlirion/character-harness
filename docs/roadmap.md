# Roadmap к автономному персонажу

Аудит состояния кода и приоритеты на 2026-11-07: [обзор проекта](reviews/current-state-review.md). Веб-панель владельца доступна на `/` core после запуска Compose; ей нужен `OWNER_TOKEN`.

## Цель

Персонаж постоянно присутствует в мире, понимает игроков в тексте и голосе, помнит проверенные эпизоды и договорённости, уместно проявляет инициативу, безопасно выполняет совместные действия и честно сообщает о результате. Автономность ограничивается явной политикой полномочий, бюджетами, возможностью паузы и проверкой внешнего эффекта.

«Максимальное взаимодействие» измеряется добровольным участием игроков, качеством продолжения общих сцен и памятью между сессиями, а не частотой сообщений. Персонаж должен уметь промолчать.

## Этап 0 — наблюдаемость и эксплуатационный цикл

- [x] Локальная веб-панель: состояние core/БД, персонажа, активного события/задачи, очереди, прямого UnionClef MCP статуса и Telegram account/bindings.
- [x] Добавить heartbeat от Pi/Codex engine, audio worker и TTS service с состоянием и безопасным кодом ошибки; панель помечает сигнал stale через 30 секунд.
- [x] Разделить ответственность: UnionClef MCP выполняет игровые действия, Fabric companion передаёт чат, STT и session-scoped наблюдения; действия bridge выключены.
- [x] Показывать в панели доступность chat ingress, Simple Voice Chat/STT и статус наблюдений.
- [ ] Проверить live-подключение bridge после перезапуска тестового клиента и отразить в панели активный сервер/session ID.
- [ ] Показывать в панели runtime policy, блокировки/причины отказа, последние действия Minecraft и подтверждение доставки речи.
- [ ] Добавить журнал последних решений и эффектов с безопасным отображением причин; owner actions (pause/resume, retry, cancel) выводить только после подтверждения идемпотентности и UX.
- [ ] Сверить инструкции развёртывания и статусные документы с текущими Compose профилями и актуальными live-проверками.

Готовность: оператор видит состояние каждого компонента, текущую цель персонажа, последние события, ожидающие решения и конкретную причину остановки без просмотра логов контейнеров.

## Этап 1 — закрыть живой социальный вертикальный срез

- [ ] Проверить live Minecraft chat ingress, reply delivery, дедупликацию и восстановление после reconnect.
- [ ] Проверить входящий SVC/STT и автоматическую слышимость ответа через Simple Voice Chat с двумя участниками.
- [ ] Проверить сквозной путь в Telegram Bot API: личка, тестовая группа, решение reply/silence, группа после approval, pause и доставка/unknown без дублей.
- [ ] Проверить один разговорный эпизод и одно обязательство после перезапуска: корректное узнавание в исходной аудитории, отсутствие ложной межканальной привязки.
- [ ] Зафиксировать пилотный сервер, персонажа, группу тестеров, правила поведения и критерии социального успеха.

Готовность: реальные игроки могут поговорить с Ладой текстом и голосом, сделать совместное ограниченное действие и вернуться к теме позже; каждый эффект проверяется в игре, а не выводится из ответа модели.

## Этап 2 — надёжность и объяснимое исполнение

- [ ] Добавить устойчивое состояние задач/навыков, отмену, контрольные точки и согласование состояния после рестарта/разрыва соединения для Minecraft операций.
- [ ] Сохранить session fencing для входящих bridge событий и усилить MCP action fencing, если UnionClef начнёт отдавать server identity и generation/session ID.
- [ ] Добавить быстрые реакции вне LLM: опасность, остановка, disconnect, игрок рядом, занятый разговорный канал и защита от повторов.
- [ ] Сделать нагрузочные/длительные проверки очередей, lease/fencing, event dedup, неизвестного исхода внешнего действия и восстановления процессов.
- [ ] Определить и показывать бюджеты по inference, действиям, времени и социальным сообщениям.

Готовность: прерванное действие не повторяется вслепую; после восстановления агент определяет наблюдаемое состояние и продолжает, ждёт или просит владельца о помощи.

## Этап 3 — постоянная инициатива

- [ ] Уточнить модель goals/needs персонажа и приоритеты между договорённостями, запросами владельца, безопасностью и спонтанной социальной инициативой.
- [ ] Поднять runtime на постоянно доступном хосте; обеспечить scheduler/wakeups между диалогами, восстановление после рестарта и операторскую паузу.
- [ ] Проверить самостоятельную работу в Telegram группе: редкие полезные инициативы, соблюдение quiet hours/лимитов, отмена при отзыве approval и проверенная доставка.
- [ ] Добавить продолжение Minecraft занятий между сессиями только при подключённом клиенте; при отсутствии клиента хранить задачу в ожидании, не имитировать присутствие.
- [ ] Ввести социальные метрики и журналировать исходы: повторный добровольный контакт, участие нескольких игроков, успешное продолжение общего эпизода, interrupt/жалобы и доля полезных молчаний.

Готовность: персонаж самостоятельно выбирает и возобновляет небольшие цели, остаётся ненавязчивым, а владелец видит почему он проснулся и что разрешило действие.

## Этап 4 — качество личности, памяти и multi-character

- [ ] Завершить социальную непрерывность Лады по [плану](social-continuity-plan.md): факты с источником и доверием, отношения на подтверждённых эпизодах, обязательства и их исполнение.
- [ ] Добавить безопасное редактирование/забывание памяти, исправление игроком, срок годности фактов, конфликтующие сведения и раздельные аудитории.
- [ ] Ввести набор оценки характерности, полезности, инициативы, перебивания, точности воспоминаний и устойчивости к prompt injection; сравнивать версии до выкладки.
- [ ] Проверить двух персонажей и несколько аудиторий в одном runtime без смешения идентичностей, памяти, полномочий и бюджетов.

Готовность: разные персонажи сохраняют отличимый голос, узнают только на основании явной/проверяемой связи и не превращают предположения в биографические факты.

## Этап 5 — мастерская способностей и улучшение

- [ ] Реализовать каталог версионированных навыков, их входные/выходные схемы, полномочия, владельца и rollback.
- [ ] Создание нового навыка сначала ограничить proposal → sandboxed evaluation → review → явный rollout; generated code не получает дополнительные права.
- [ ] Отдельно построить replay/evaluation набора трасс, регрессионные проверки политики и отчёт причин улучшения.
- [ ] Автоматическое продвижение версии включать только после измеримого улучшения и прохождения safety/character regression gates.

Готовность: персонаж может предложить полезный навык, но исполняемая версия появляется только после проверок и может быть быстро откачена.

## Технические проверки, которые не считаются готовностью пилота

PostgreSQL/TypeScript/Java/Python автотесты подтверждают локальные контракты. Они не доказывают live inference, слышимость вторым игроком, прохождение навигации в мире, корректность долгой автономной работы или социальную ценность. Все эти проверки фиксируются как отдельные результаты в [журнале](journal.md).
