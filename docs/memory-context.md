# Память и оптимизация контекста

## Слои памяти

Рабочее состояние хранит текущую цель и активный навык. Эпизодическая память — попытки и результаты. Семантическая — факты. Процедурная — проверенные стратегии. Обязательства хранят обещания, ограничения и ожидаемые ответы.

Факты имеют источник, область видимости, время, уверенность и срок актуальности. Наблюдаемое, предполагаемое и желаемое состояния различаются. Противоречия разрешаются явно; старые сведения не заменяются молча.

```text
Наблюдение -> кандидат -> проверка -> дедупликация
-> разрешение противоречий -> сохранение
```

Журнал событий — первичная история. Индексы и сводки являются производными данными.

## Сборка контекста

Контекст собирается под очередное решение:

```text
Политика + цель + критерии успеха + состояние
+ активный план + обязательства + существенные события
+ найденная память + нужные схемы инструментов
```

Отбор учитывает релевантность, свежесть, достоверность, последствия пропуска и стоимость токенов. Критические ограничения закрепляются независимо от рейтинга.

В текущем игровом срезе оба движка получают общий `turn_input`: последние десять завершённых пользовательских сообщений до текущего события, с ответом Лады либо явным `assistant_silent: true`, долговременными заметками и bounded social memory. История ограничена теми же character и audience, выводится в хронологическом порядке и занимает не более 8 000 сериализованных символов. Текущие, будущие и незавершённые события в историю не попадают. Участники различаются непрозрачными speaker refs; сырые внешние IDs не передаются в модельный контекст. Provenance остаётся у каждой записи памяти.

Социальные записи хранятся отдельно в `social_people`, `social_facts`, `social_relationships`, `social_commitments` и `social_working_states`. Все записи ограничены character и audience. Ключ человека — пара channel/external id; имя и одинаковый внешний идентификатор в разных каналах не связывают профили. Контекст приоритизирует текущие открытые обязательства и отношения с provenance; каждый блок ограничен общим бюджетом 6 000 сериализованных символов. О пропуске обязательств сообщает `omitted`, подробности доступны страницами через `memory_social_list` (до 25 записей на страницу, offset до 500). Источники указывают на события той же области видимости. Engines передают proposal через MCP `memory_stage_delta`; core подставляет доверенные event/epoch/участника, а атомарное применение происходит с reply и optional speech при `/engine/complete`. Невалидный delta или конфликт версии не отменяет ответ. `memory_stage_delta` не публикует незавершённый turn.

Owner endpoint `/owner/inspect-context` показывает реконструкцию текущего bounded input для выбранного pending event и метрики отбора. Он не захватывает lease, не запускает inference и не раскрывает persona. Результат отражает память на момент просмотра, а не исторический snapshot уже исполненного turn.

Текущая версия UnionClef MCP не передаёт входящие игровые chat/voice события. Minecraft observation поступает read-only через `getGameState`, и считается непроверенным состоянием мира. Engine adapter завершает каждый модельный turn локальным typed `turn_finish`; без реального входящего игрового события агент не просыпается от сообщений в Minecraft.

## Механизмы

- Агрегация частых событий вместо включения каждого тика.
- Структурные сводки с фактами, препятствиями и открытыми вопросами.
- Загрузка подробностей по ссылкам при необходимости.
- Выбор ограниченного набора инструментов для текущей задачи.
- Резерв бюджета для ответа и результатов инструментов.
- Кеширование стабильных частей при поддержке модельного API.
- Пересборка контекста при повторных ошибках и отсутствии прогресса.

Сводки сохраняют идентификаторы, обязательства, ограничения, незавершённые действия и доказательства. Их следует восстанавливать из исходных событий и состояния, избегая цепочек пересказов.

Качество оптимизации оценивается по успешности задач и числу пропущенных важных фактов, а не только по сокращению токенов.
