# Общая память персонажей: варианты и рекомендация

Дата: 2026-10-04. Исследовательское предложение для MVP. Код и миграции не реализованы; решение требует фиксации в ADR после выбора владельцем. Прочитаны README, memory-context, characters, persistent-agents, implementation-options и product-plan; применимые AGENTS.md в каталогах проекта и предках не найдены. Другие документы не изменены.

## Что значит «общая память»

Предлагаю одну PostgreSQL для всех экземпляров, но разные личные памяти и отдельную общую библиотеку знаний. Два персонажа могут знать, где стоит сундук, сохраняя разные воспоминания о том, как нашли его. Они не должны автоматически получать одинаковые отношения, привычки и биографию.

Общая инфраструктура — место хранения. Общие знания — записи, которым явно разрешено совместное использование. Это разные решения. Центральный доступ через core/MCP нужен при любом варианте; он не требует отдельного микросервиса.

| Вид данных | Кто владеет | Как делиться |
|---|---|---|
| Факты мира | Конкретный мир/сервер/измерение | Проверенные наблюдения доступны участникам заданной команды; права на сообщение наружу проверяются отдельно |
| Эпизоды и отношения | Экземпляр персонажа | По умолчанию личные; можно опубликовать извлечённый факт без передачи биографии |
| Память владельца | Владелец и источник общения | Предпочтения и личные сведения получают только назначенные персонажи/контексты; нет автоматической доступности всем агентам владельца |
| Задания и обязательства | Владелец задачи + исполнитель | Структурные таблицы core с ACL; доступ помощника выдаётся на конкретную задачу |
| Навыки и инструменты | Реестр версий | Допущенные артефакты распространяются по политике; воспоминание об успехе навыка само по себе не допускает код |
| Пакет личности | Автор/владелец пакета | Версионированная конфигурация; новая установка копирует исходные знания, а не чужую биографию |
| История движка | Экземпляр + security domain + purpose | Не объединяется между аудиториями; архив и snapshot имеют собственные ограничения |

Секреты, Telegram StringSession и ключи модели вообще не являются памятью агента: они остаются в адаптерах.

## Варианты

| Подход | Как работает | Преимущества | Основные риски | Пригодность |
|---|---|---|---|---|
| A. Общая таблица с областями доступа | Все записи сразу находятся в одном логическом пространстве; фильтры определяют доступ | Самый короткий путь, минимум копирования | Ошибочная широкая метка сразу распространяет факт; трудно отличить общую истину от личного мнения | Подходит для маленькой доверенной группы, если публикация всё равно контролируется |
| B. Личные памяти + явная публикация | Наблюдения/эпизоды остаются личными; отдельная запись знания публикуется в мир/команду | Понятный владелец и граница передачи; сохраняет характер; публикацию можно проверить и отозвать | Дополнительный шаг; нужны связи оригинала и публикации, разрешение конфликтов | Рекомендовано для MVP; реализуется в той же PostgreSQL |
| C. Knowledge service / blackboard | Агенты размещают утверждения и запросы; служба ведёт канонические объекты, согласование, подписки | Хорош для многих персонажей и совместных задач; единая политика актуальности | Сложнее протокол, больше зависимостей; центральная ошибочная «истина» влияет на всех | В MVP — модуль MemoryService внутри core; отдельный сервис и развитый blackboard позже |

Варианты не взаимоисключающие. Рекомендация B использует общую SQL-базу из A и небольшой центральный API из C. Отличается именно политикой публикации, а не количеством контейнеров.

## Рекомендуемый MVP

1. Один `MemoryService` внутри доверенного core; engine видит его только через MCP.
2. PostgreSQL: личные эпизоды, факты, источники, публикации и метки доступа; задачи/навыки сохраняются в своих таблицах.
3. Личная запись по умолчанию. В общий мир автоматически публикуются только разрешённые схемы фактов, подтверждённые адаптером: например местоположение общего сундука. Свободный текст и сведения из приватного чата автоматически не расширяют аудиторию.
4. SQL по структурным ключам плюс полнотекстовый поиск. Нет обязательных embeddings, графовой БД и memory framework.
5. Отдельные сессии движка для приватного Telegram, конкретной группы, публичного Minecraft-чата, внутренней работы и мастерской. Передача между ними только через проверенный пакет фактов/результата.
6. Общие факты передаются при следующей сборке контекста, а критические изменения порождают событие. Не пытаться мгновенно переписать историю всех активных сессий.

Полезно начинать с одного активного экземпляра, но модель данных и тесты доступа сразу проверять на двух. Одновременная игра двух персонажей — отдельный технический этап, не условие внедрения общей базы.

## Примеры

**Север и Искра в одном Minecraft-мире.** Север нашёл общий склад в `world-1/overworld/120,64,-30`. Он сохраняет личный эпизод «я нашёл склад после похода». Адаптер подтверждает координаты; MemoryService публикует факт `warehouse.location` для команды этого мира. Искра получает координаты, но не чужой эпизод или отношение к владельцу склада. Если сервер сброшен, меняется `world_generation_id`; прежние координаты не применяются к новому миру.

Искра наблюдает в сундуке 12 железных слитков, Север позже — 4. Это последовательные снимки запаса с временем и source event, а не конфликт двух вечных истин. Перед расходованием ресурса worker перечитывает инвентарь. Если оба сообщили разные значения за одну версию состояния, факт помечается disputed и выполняется повторное наблюдение. План распределения ресурсов хранится в задачах/резервациях, а не в текстовой памяти.

**Личный Telegram.** Владелец сообщил Северу приватную причину своего отсутствия и поручил поддерживать запас дерева. Причина остаётся в домене диалога. В игровой worker передаётся минимальное поручение «поддерживать запас», без причины и исходной цитаты. Это очищенная передача конкретной задачи, которую разрешает core; её нельзя получить произвольным переписыванием секрета моделью. Предпочтение владельца не становится общим только потому, что все агенты принадлежат ему.

**Группа Telegram.** В разрешённой группе игрок сообщил «мост повреждён». Запись сохраняет группу как источник и ограничение аудитории. Проверенный worker факт состояния моста может быть опубликован в команду мира, если такая передача разрешена владельцем. Личная оценка игрока «Искра меня раздражает» не становится отношением всех персонажей. Общий факт «склад доступен команде» ещё не разрешает опубликовать его координаты в посторонней группе.

## Социальный MVP: узнавание без коллективной личности

Подтверждённый продуктовый приоритет — социальный вау-эффект для участников Minecraft-сервера и Telegram. Поэтому в первом наборе важны не только координаты: узнавание знакомого игрока, упоминание совместного публичного события и выполнение обещания.

Нужен небольшой реестр `people` и `identity_links(person_id, platform, binding_id, external_account_id, verified_by, verified_at, revoked_at)`. Межканальная идентичность связывается явно владельцем или проверяемым действием участника; одинаковый ник, стиль письма или предположение LLM не достаточны. Имена не являются ключами идентичности.

Север и игрок вместе пережили публичное нападение. Север хранит личный эпизод и своё отношение; общий слой может хранить факт события с участниками и разрешённой аудиторией. Искра может знать, что событие произошло, но не заявляет «я помогала тебе», если её не было. При встрече игрока в связанной Telegram-группе Север может вспомнить событие только если межканальная публикация разрешена. В приватном диалоге тот же игрок рассказал причину своего страха: публичное узнавание не раскрывает её.

Обещание «завтра починю твой мост» становится task/commitment с автором, адресатом, сроком, источником и аудиториями уведомления. Оно закрепляется в контексте и scheduler, а не остаётся только поисковым эпизодом. Передача обещания Искре требует явного назначения; Север сообщает о делегировании там, где это уместно. Личные отношения хранятся как `character → person` с evidence и не усредняются по всем агентам. Приватные негативные оценки не публикуются автоматически.

Социальный приёмочный сценарий: два персонажа и один участник, совместное событие в игре, явно связанный Telegram-аккаунт, последующая встреча, обещание и перезапуск. Проверяется правильное узнавание, отсутствие выдуманного участия, сохранение обещания и отсутствие переноса приватной детали. Оценку естественности даёт участник; простого совпадения имени недостаточно.

## Две независимые границы доступа

У записи есть `reader_domain_id` (кто может использовать знание) и `disclosure_domain_id` (где можно раскрывать его содержание). Это не одно поле `public/private`. Например, внутренняя команда может прочитать операционный результат, но сообщать его можно только владельцу задачи.

В MVP безопасный контекст публичного ответа содержит только записи, разрешённые и на чтение, и для этой аудитории. Внутренний контекст с приватными сведениями не имеет инструментов отправки публичного текста. Адаптер MCP не может надёжно обнаружить произвольный перефразированный секрет в ответе; изоляция входного контекста важнее попытки фильтровать выход.

`domain_members` задаёт разрешённые principal: экземпляры, владельца, группы. Вступление нового персонажа в команду или нового человека в группу не означает автоматического раскрытия всей прежней истории: политика должна определить применимость старых записей и membership epoch. До этого решения — запрет расширения аудитории старого приватного материала.

## Минимальная схема PostgreSQL

Предлагаемая логическая схема; SQL-миграции следует написать после проверки контрактов. UUID для внутренних идентификаторов, внешние account/chat/world ids — отдельные поля без вывода секретов.

```text
memory_domains(id, owner_id, kind, binding_id, membership_epoch)
domain_members(domain_id, principal_type, principal_id, joined_at, revoked_at)

memory_sources(id, event_id, source_kind, source_binding_id,
  reader_domain_id, disclosure_domain_id, observed_at,
  external_message_id, source_version, payload_ref, deleted_at)

memory_records(id, owner_id, character_id nullable,
  kind [fact|episode|relationship|owner_preference|summary],
  world_generation_id nullable, entity_key nullable, predicate nullable,
  content jsonb, search_text, search_vector tsvector,
  reader_domain_id, disclosure_domain_id,
  status [candidate|active|disputed|superseded|expired|deleted],
  evidence_kind [observed|reported|inferred], confidence nullable,
  observed_at, recorded_at, valid_from, valid_until,
  version, supersedes_id nullable, created_by)

memory_lineage(record_id, source_id nullable, parent_record_id nullable)
  -- ровно одна ссылка на строку; производная запись обязана иметь lineage
memory_publications(id, source_record_id, published_record_id,
  target_reader_domain_id, target_disclosure_domain_id,
  status, policy_version, approved_by, reason, created_at)
memory_audit(id, principal_id, operation, record_ids,
  turn_id, policy_version, outcome, created_at)
```

Индексы: B-tree по доменам/статусу/актуальности, `(world_generation_id, entity_key, predicate)`, GIN по `search_vector`. Дедупликация источника — UNIQUE по binding + внешнему event id; idempotency key для записи — отдельная уникальная таблица запросов или существующий механизм core. `character_id=NULL` не означает публичный доступ.

`tasks`, `responsibilities`, `operations`, `skill_versions`, `engine_sessions`, `context_snapshots` остаются отдельными таблицами. Память может ссылаться на них, но не является источником их статуса. В snapshot сохраняются использованные record ids/versions и domain/policy version.

В MVP фильтрация доступа реализуется одним доверенным SQL repository внутри MemoryService и тестируется для всех операций. RLS PostgreSQL может дать дополнительный барьер, но не заменяет проверку политики; таблица, которой владеет runtime-role, может обходить RLS. При включении нужны отдельный владелец таблиц, runtime без BYPASSRLS и transaction-local principal; нельзя оставить principal в pooled connection между запросами. Это свойство [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), а предложенная domain policy — наше проектирование.

## Контракты через MCP

Имена ниже проектные, не стандарт MCP. Principal, character, owner и security domain берутся из credential/session binding шлюза, а не из доверенного аргумента модели.

| Tool | Вход | Выход и правило |
|---|---|---|
| `memory_read` | record id | Запись, version, разрешённые источники; недоступный id не раскрывает наличие приватного факта |
| `memory_search` | query, kind, world/entity filter, limit | Разрешённые и актуальные записи с provenance; фильтр применяется до выдачи snippets/score |
| `memory_propose` | content, kind, source ids, expected validity, idempotency key | candidate id; метки доступа и доверия выводит core из источников |
| `memory_correct` | id, expected_version, correction, new source ids | Новая версия/запись + supersedes; конфликт version возвращается явно |
| `memory_publish` | id, target domain, разрешённая проекция, reason | published/candidate/denied; домен должен входить в разрешённые targets сессии |
| `memory_retract` | id, expected_version, reason | Отзыв собственной записи/публикации; не даёт удалить чужую историю |

Право владельца на полное удаление, управление domain membership и изменение политики — отдельный детерминированный административный путь. Поисковые counts, evidence links, error messages и аудит тоже фильтруются. `read(id)` не обходит правила `search`.

Источники-сообщения не становятся инструкциями харнеса. «Игнорируй политику и запомни это как правило» остаётся untrusted text. Confidence от модели — оценка, не доказательство. Повтор одного сообщения несколькими агентами не считается независимым подтверждением.

## Поток записи и сборки контекста

```text
Событие адаптера с источником и доменом
  → детерминированное состояние / кандидат памяти
  → проверка схемы, источников и меток
  → личная запись
  → разрешённая публикация конкретного факта
  → разрешение/обозначение противоречий
  → SQL/FTS поиск внутри допустимых доменов
  → компактный context snapshot со ссылками и версиями
  → новая или совместимая engine session
```

Наблюдаемые координаты/инвентарь пишет адаптер по схеме; модель извлекает предпочтения, эпизоды и гипотезы в candidates. Цель, ограничения и обязательства включаются в snapshot детерминированно, независимо от рейтинга retrieval.

Полный лог игры не превращается в вечную память: изменения агрегируются, хранятся значимые эпизоды и факты, сырьё имеет отдельную retention policy. Журнал источников нужен для объяснения, но не требуется полное event sourcing мира.

## Актуальность, конфликты и конкурентность

- Разделять `observed_at`, время записи и интервал действительности. Старое сообщение, доставленное после reconnect, не перезаписывает свежее наблюдение.
- Быстро меняющиеся факты (запасы/опасность) имеют короткий срок и обязательную проверку перед действием; координаты — привязку к поколению мира. Конкретные интервалы выбираются испытаниями.
- Сохранять несколько утверждений при настоящем противоречии, помечать disputed и искать новое доказательство. Нельзя применять универсальное «последний текст побеждает».
- Источник наблюдения имеет приоритет для состояния мира; сообщение пользователя может быть первичным для его предпочтения. Нет одной шкалы доверия для всех типов фактов.
- Core транзакционно сериализует обновление канонического ключа факта; optimistic version/CAS предотвращает потерянное исправление. Создание первого ключа защищено UNIQUE и повтором после конфликта; блокировка отсутствующей строки сама по себе не помогает.
- Для резервирования предметов нужна транзакция отдельного учёта ресурсов; актуальная память не предотвращает двух одновременно исполняемых действий.

PostgreSQL поддерживает блокировки строк, включая `SELECT FOR UPDATE`; выбор таблиц, CAS и ключа факта — проектное решение. [Документация блокировок](https://www.postgresql.org/docs/current/explicit-locking.html).

## Сводки, embeddings и удаление

Сводка наследует пересечение допустимых читателей и аудиторий всех своих источников. В MVP сводки формируются отдельно для одного security domain; объединение разных доменов не допускается без явного разрешения. Embedding, snippet и поисковый индекс сохраняют те же ограничения, source version и связь с оригиналом. Перефразирование не снимает метки приватности. Расширение возможно только отдельной проверенной публикацией с явной проекцией и основанием.

Исправление отзывает/помечает старую запись и все зависимые публикации/сводки для пересборки. Soft delete прекращает retrieval, но не является полным удалением. Полное удаление владельцем удаляет содержимое, индексы, производные артефакты и связанные сохранённые engine contexts; в аудите остаётся только разрешённый минимум метаданных без текста. Backups имеют описанный срок удержания; невозможно обещать немедленное стирание из всех резервных копий. Уже отправленное внешнему провайдеру или опубликованное сообщение нельзя считать отозванным удалением строки в SQL.

## История Pi/Codex — отдельная поверхность памяти

Фильтр `memory_search` не удаляет факт, уже попавший в сохранённую историю движка или компактированную сводку. Поэтому один персонаж не должен иметь одну бесконечную engine session на все каналы.

Привязка: `(character_instance, security_domain, purpose, policy_epoch)`; закрытая задача может знать приватное, публичная сессия получает только разрешённый snapshot. Новая аудитория, отзыв доступа или загрязнённый контекст требуют новой сессии, очищенного snapshot и архивации старой, а не добавления сообщения «забудь секрет». Snapshot version проверяется перед продолжением после рестарта. Старую сессию нельзя автоматически восстановить под новым domain binding.

Фоновая задача с приватными сведениями не публикует свободный итог напрямую. Core передаёт минимальный проверенный результат публичной сессии; для игрового действия использует структурный operation contract. Возможности очистки/восстановления Pi/Codex нужно доказать spike, как указано в implementation-options. Это требование нашей архитектуры; здесь не предполагается API произвольного редактирования engine history.

## Нужны ли vectors, граф и frameworks

| Технология | Сейчас | Когда добавлять | Что измерять |
|---|---|---|---|
| SQL + FTS | Да: явные ключи фактов, русскоязычный текст и GIN | Базовый вариант | Recall нужных фактов, пропуски обещаний, latency, стоимость успешной задачи |
| pgvector | Отложить; семантическая память не требует семантического поиска | Перефразированные запросы регулярно теряют полезные записи в FTS | Сравнить FTS и hybrid на одном размеченном наборе, отдельно после ACL-фильтра |
| Таблицы связей в PostgreSQL | Простые relations при реальной потребности | Связь персонаж→игрок/место/объект помогает сценарию | Правильность связей, разрешение одинаковых имён |
| Отдельная graph DB | Нет | Подтверждённые многопереходные запросы и объём, неудобные для SQL | Прирост качества относительно SQL joins/recursive queries и цена эксплуатации |
| LangGraph store / Letta / Mem0 | Не вводить вторую систему состояния | Нужная готовая функция даёт измеримую экономию разработки | ACL, provenance, экспорт/удаление, совместимость Pi/Codex и качество на нашем наборе |

PostgreSQL предоставляет полнотекстовый поиск. [Документация FTS](https://www.postgresql.org/docs/current/textsearch.html). Русский текст тестируется выбранной конфигурацией, игровые ids ищутся структурно; нельзя полагаться на морфологию для координат.

pgvector поддерживает точный и приближённый поиск; при approximate index фильтрация может уменьшать число найденных разрешённых результатов, iterative scans помогают управлять recall. Индекс не реализует ACL сам: search, counts и результаты проверяет core. На маленьком разрешённом наборе сначала проверить exact search без ANN. [README pgvector](https://github.com/pgvector/pgvector).

## Что подтверждают первичные источники

Источники проверены 2026-10-04. Они подтверждают механизмы и существование подходов, но не работоспособность предложенного харнеса.

- [Generative Agents, Park et al.](https://arxiv.org/abs/2304.03442): архитектура с памятью опыта, reflection и извлечением для планирования; полезный исследовательский ориентир для персонажей. Не доказательство безопасности совместной памяти или production-надёжности.
- [LangGraph memory overview](https://docs.langchain.com/oss/javascript/concepts/memory): разграничивает thread-scoped историю и long-term namespaces, описывает semantic/episodic/procedural memory и запись в ходе работы/фоном. Namespace — организация данных, сам по себе не гарантия полномочий.
- [Letta memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks): документирует общие блоки для нескольких агентов и read-only блоки. Это реальный вариант shared memory; блоки в контексте требуют самостоятельного решения аудитории. Страница относится к V1 SDK и помечена legacy, поэтому API не принимается как зависимость проекта.
- [Mem0, официальный репозиторий](https://github.com/mem0ai/mem0): пример add/search с user filters и отдельный memory layer. Его маркетинговые показатели не переносятся на наш MVP; фильтр user_id не заменяет наши reader/disclosure domains.
- PostgreSQL и pgvector выше подтверждают возможности хранения, поиска и конкурентной записи. Таблицы, domain policy, публикация, временная модель и session isolation в этом документе — собственное проектирование.

## Приёмочные проверки

1. Север публикует координаты: Искра видит факт и доступное доказательство, но не личный эпизод. Другой мир/владелец не получает запись даже по известному id.
2. Приватный Telegram-факт отсутствует в групповом и игровом snapshot, в поисковых counts, snippets и tool errors; после compaction/restart тест остаётся успешным.
3. Старая приватная Pi/Codex session не восстанавливается для публичной аудитории. Отзыв доступа повышает policy epoch и инвалидирует зависимый контекст.
4. Повтор события не создаёт новые копии. Старое наблюдение после reconnect не побеждает свежий inventory snapshot.
5. Одновременные исправления дают version conflict или сериализованный результат; ни одно подтверждённое изменение не теряется молча.
6. Disputed факт виден как спорный, перед действием происходит сверка; reported/inferred не выдаются за observed.
7. Удаление/исправление затрагивает опубликованную копию, сводку и будущий embedding; тест включает сохранённый engine context.
8. Новый член группы/команды не получает старые приватные записи без политики. Навык не допускается только потому, что есть положительное воспоминание.
9. После рестарта сохранены обещания и обязательства независимо от top-k retrieval. Число токенов уменьшается без ухудшения выполнения контрольных задач.

Размеченный набор должен содержать ожидаемые факты и допустимые аудитории, варианты перефразирования и устаревания. Измерять recall@k, долю устаревших/ложных фактов в контексте, нарушения аудитории, забытые обязательства и стоимость проверенного результата. Целевой результат тестов доступа — ноль утечек; это критерий допуска набора, не абсолютная гарантия эксплуатации. Порог поиска выбирается после базового измерения, без выдуманного универсального значения.

## Вопросы владельцу

1. Персонажи — команда с обменом знаниями или независимые личности, которым нужно рассказывать друг другу новости? Рекомендация: общие проверенные факты мира, личные отношения.
2. Какие знания Minecraft можно раскрывать в Telegram-группах и наоборот? По умолчанию только явно связанные команда/мир/группа.
3. Предпочтения владельца автоматически доступны всем его персонажам или только назначенным? Рекомендация: явное назначение.
4. Новые участники получают прежние общие знания команды? Для приватной переписки по умолчанию нет; для справочника мира возможно отдельное разрешение.
5. Нужно ли агентам сохранять спорные убеждения как часть характера? Рекомендация: да в личной памяти, но общий слой не объявляет их истиной.
6. Какие совместные публичные события и обещания создают желаемый социальный эффект? Социальный сценарий уже приоритетен; уточнить конкретное событие, допустимые каналы узнавания и форму реакции.

Ответы уточняют политику. Схему личной памяти и API можно начать реализовывать без решения всех вопросов, сохраняя закрытые defaults.
