# Разбор независимого ревью Astra

Дата: 2026-10-04. Основа: [ревью Astra](astra-review.md), [roadmap](roadmap.md), [продуктовые эпики](product-plan.md), текущий первый инфраструктурный срез. Ниже — рекомендации основного агента; это не утверждение пользователем образа, пилота или ограничения продукта.

## Вывод

Ревью полезно прежде всего как коррекция порядка разработки и критериев успеха. Оно не требует смены Pi/PostgreSQL/MCP/Docker. Главная подтверждённая проблема документов: нумерованный roadmap откладывает личность и память после широкого runtime, хотя продуктовый план уже ставит социальный опыт первым. В коде пока есть инфраструктурный фундамент, а не социальный персонаж.

Историческая оговорка Astra о недоступности Docker устарела: сборка, миграции, typecheck, четыре policy-теста и MCP/SQL smoke теперь прошли. Ревью остаётся оценкой замысла, не аудитом работоспособности адаптеров.

## Что принять в ближайшую реализацию

| Рекомендация | Следствие для харнеса |
|---|---|
| Характер проявляется в выборе | Пакет персонажа: мотив, предпочтения, границы спора, примеры выбора и исправления; короткий одинаковый набор сцен для проверки пакетов |
| Отношения опираются на общие эпизоды | Разделить наблюдаемое событие, утверждение участника и интерпретацию агента; у каждого источники, участники, аудитория и возможность исправления |
| Каналы имеют разные формы общения | Общая идентичность персонажа, отдельные контексты каналов; явная связь аккаунтов и отдельное разрешение переносить эпизод |
| Голос должен быть актуальным | Очередь коротких реплик, адресат/повод/срок актуальности; перед воспроизведением проверка мира и отмены; отсутствие STT обозначается в демо |
| Инициатива завершается при молчании | Сохранённые повод, статус приглашения и срок; общий лимит обращений между каналами, отказ и pause работают вне LLM |
| Успех — добровольный интерес | Различать организованное демо, ответы на инициативу и самостоятельные повторные обращения; сохранять также ошибки и вмешательства оператора |

Карточку отношений начать как представление из эпизодов, предпочтений и открытых обещаний. Отдельный граф отношений и числовой рейтинг близости пока не нужны. Социальный режим хранить минимально: занятие, адресат, ожидаемое событие, открытое приглашение. Не строить отдельную сложную систему симуляции личности до наблюдений пилота.

## Где нужна поправка или дополнительная проверка

1. Один персонаж в пилоте разумен, но универсальность — центральное требование пользователя. Схема пакета должна быть общей с начала; до завершения MVP проверить второй контрастный пакет последовательно на том же стенде, без правок ядра. Несколько одновременных экземпляров — отдельное расширение.
2. Картограф и сцена «Наше место» — удобные тестовые предложения, а не доказанный лучший продукт. Согласовать роль с реальным сообществом. Видимый результат должен быть подтверждён адаптером; слова игрока о совместном событии не доказывают участие агента.
3. TTS может дать первое впечатление, но текстовый вход ограничивает естественность голосовой встречи. STT не обязателен для теста голосового вывода; если участники общаются преимущественно голосом, его приоритет следует поднять по результатам пилота.
4. Метрика возвратов полезна, но зависит от новизны, доступности сервера и расписания игроков. Показывать числа, конкретные эпизоды, причины обращения и возможность повторной встречи. Маленький пилот не даёт оснований объявлять статистически доказанный спрос.
5. Техническую проверку голосового bridge выполнить рано: совместимость и право установить addon могут ограничить весь сценарий. Ревью не снимает этого риска.
6. Саморасширение и альтернативный движок можно отложить по объёму реализации, сохранив контракты. Отказ от этих направлений не следует из ревью.

## Что ревью недораскрыло

**Контекст.** Нужен явный context assembler: persona + текущая сцена/адресат + разрешённые релевантные эпизоды + открытые обещания + компактный каталог инструментов. У каждой части бюджет. Сначала простая выборка по участникам, месту и свежести; векторный поиск — при наблюдаемой нехватке. Исправление/исключение памяти должно инвалидировать производные сводки. Текущий код берёт до 20 заметок без релевантности конкретному событию; этого недостаточно для долгого общения.

**Анализ поведения.** Записывать происхождение повода, выбранное действие, версии пакета/контекста/инструмента, итог среды, время и стоимость, вмешательство оператора. Разметка различает ошибку памяти, выбора адресата, характера, инициативы, инструмента и устаревшую речь. Не требуется хранить скрытые рассуждения модели. Хранение разговоров зависит от политики аудитории.

**Улучшение.** Цикл: замеченный сбой → кандидат изменения → независимые контрольные сцены → сравнение с базовой версией → версия и откат. Сначала менять инструкции/процедуры из разрешённых инструментов. Автоматическое изменение личности, прав или публикация нового исполняемого кода не входит в первый пилот. Число сообщений не является единственной целевой метрикой.

**Самосоздание навыков.** Без произвольного кода возможны декларативные процедуры: разрешённые шаги, входные условия, отмена и проверка результата. Их всё равно проверять на соседних сценариях; композиция разрешённых действий может быть неуместной. Кодовый runner добавляется отдельно.

## Предлагаемый порядок следующих срезов

1. Проверить реальный Pi turn с выбранной моделью. Параллельно технически проверить Minecraft-подключение и голосовой путь на выбранном сервере.
2. Первая встреча: игровой чат, короткая речь, движение к разрешённой точке, мотив персонажа и проверяемый результат действия.
3. Эпизодическая память: источник и участники, исправление, обещание, восстановление после рестарта; затем явная связь аккаунтов и разрешённое продолжение в Telegram.
4. Свободный пилот: ограниченная событийная инициатива, общий лимит шума, простая сборка контекста и трассы поведения. Проверить второй пакет последовательно.
5. По обнаруженным ограничениям: процедуры-навыки, STT, дополнительные инструменты, Codex, общие знания и несколько экземпляров. Не задавать им жёсткую общую очередь без причины.

## Решения, реально блокирующие живую сцену

- Сервер: версия Minecraft, loader и возможность установить voice addon.
- Провайдер/модель Pi и TTS, бюджет.
- Первое сообщество, роль персонажа и разрешённое действие.
- Публичные аудитории Minecraft/Telegram и способ связывания участников.

Это не список обязательных решений перед любым следующим кодом: модельный turn, контракт пакета, трассы и context assembler можно прорабатывать независимо. Параметры сервера необходимы для совместимого живого voice bridge.
